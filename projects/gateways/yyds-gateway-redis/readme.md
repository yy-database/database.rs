# yyds-gateway-redis

Redis protocol compatibility work for YYDS. The standalone Rust `yyds-redis-server` remains a bounded RESP2 PING, ECHO and QUIT probe on IPv4 loopback. The node-owned `RedisService` additionally binds binary GET, ordered atomic MGET, single-key EXISTS, atomic GETDEL and GETSET, SET, SET NX and SET XX, single-key DEL and signed 64-bit INCR/INCRBY/DECR/DECRBY to the YYDS execution contract. Conditional set, get-and-delete, get-and-replace, increments/decrements and MGET are atomic within the current single-process executor and persisted by its mounted shard. MGET preserves request order and duplicate keys, while cross-node snapshot consistency remains outside this local contract. Other SET options and multi-key EXISTS remain unsupported. It preserves binary arguments and pipelines, limits connections to 64, and uses a bounded I/O wait.

Run `cargo run -p yyds-gateway-redis --bin yyds-redis-server -- --port 6379`, then use an original `redis-cli -h 127.0.0.1 -p 6379 PING`. The standalone binary is a protocol probe. The `yyds` CLI attaches the executor-backed service to its local `.yykv` shard. Replication, multi-key commands, SET options, SELECT, transactions, authentication, TLS and RESP3 are not implemented. The npm launcher is not yet connected to this listener.

`service::RedisService` attaches a loopback listener to an existing shared `Arc<NodeLease>` and can consume an injected `yyds-execution::KeyValueExecutor`. It retains that node owner until its accept and client workers finish. Explicit stop or drop interrupts idle and partially received connections and joins all workers before releasing ownership. Failed binds release their owner reference without starting workers. The current `LocalExecutor` is single-process and does not prove replication or cluster health.
